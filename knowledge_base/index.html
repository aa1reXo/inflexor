Portfolio Knowledge Base — System Architecture

A queryable memory layer across ~30 portfolio companies — SHAs, term sheets, board decks, and a continuously-updated stream of call transcripts — answering both numeric questions ("revenue last 3 months?") and qualitative ones ("key risks right now?") with citations. Four named services move data through it: Hermes pulls it in, Argus classifies and extracts it, Atlas holds it, Delphi answers questions from it. How each step works

The diagram above is the real data flow — nothing decorative. Each card below expands the node it's named after; click a node up top and it'll scroll here and highlight.

HERMES — Ingestion

Five inbound paths, one normalized intake
📤

Manual Upload

The fallback path for anything that doesn't arrive automatically — a partner drags a signed SHA or a one-off PDF into the dashboard. Lowest volume, highest variance in format, so it goes through the same classifier as everything else rather than a special-cased path.

Triggerpresigned S3 upload · React dropzone
📧

Shared Inbox

A dedicated address (e.g. portfolio@) that partners and founders CC or forward to. Attachments are pulled automatically; the email body itself is kept as context (it often explains what changed) rather than discarded.

TriggerGmail API · Pub/Sub push
🗂️

Google Drive

Per-company watched folders, polled on a schedule via the Drive API. This is where most existing SHAs, term sheets and board decks already live today, so it's treated as the primary bulk-backfill source during initial rollout, not just a trickle feed.

TriggerDrive API v3 · changes.list
🔗

DocSend Links

Data-room and deck links shared by founders don't come as files — they're fetched (where access allows) and snapshotted so the knowledge base isn't dependent on a link staying live. Anything that can't be fetched automatically falls back to a manual-upload prompt.

TriggerPlaywright headless fetch + snapshot
⚡

Call Transcripts

The two tools plug in differently, so the connector has to handle both patterns rather than treating them as interchangeable. Fireflies has a native webhook — a "transcription complete" event posts straight to an endpoint the moment a call is processed. Granola's API access is Enterprise-plan only (it also exposes an MCP server for agent-based access); short of that tier, ingestion runs through a Zapier-mediated webhook instead. Either way, a new transcript lands in the pipeline within minutes of the call ending, not on a batch delay.

TriggerFireflies webhook · Granola Enterprise API/MCP

ARGUS — Classify & Extract

One router, two parallel pipelines, one confidence gate
🔍

Doc-Type Classifier

A cheap, fast model looks at the incoming document (or transcript) and tags it: term sheet, SHA, board deck, financial statement, call transcript, other. This tag decides which extractor(s) it's routed to next — it's the fork point between the structured and unstructured pipelines. Every raw file is also archived to object storage at this step, unconditionally, before anything else happens to it.

ProcessingClaude Haiku 4.5 · structured output
🧮

Structured Financial Extractor

For financial statements and reports: a schema-enforced (JSON-mode) LLM call pulls specific fields — revenue, burn, runway, headcount — into a fixed structure rather than free text. This is what makes "what was revenue last 3 months?" a deterministic lookup later instead of a guess.

AI stepClaude Sonnet 5 · JSON mode + Pydantic schema
⚖️

Legal Term Extractor

For SHAs and term sheets: another schema-enforced call, but tuned to legal structure — liquidation preference, anti-dilution, board composition, ESOP terms, information rights. Same principle as the financial extractor: turn prose into queryable fields instead of leaving it as text a model has to re-read every time.

AI stepClaude Sonnet 5 · JSON mode + Pydantic schema
📝

Transcript Summarizer

Raw call transcripts are long and noisy. Before embedding, each transcript is passed through a summarization step that produces a structured call note (topics discussed, decisions, action items, risks flagged) — this is what actually gets embedded alongside the raw transcript, so retrieval later surfaces the signal, not filler.

AI stepClaude Haiku 4.5 · map-reduce summarization
🧩

Chunk + Embed

Everything that isn't cleanly structured (board deck prose, transcript summaries, qualitative sections of any document) is semantically chunked — tight, topic-coherent chunks rather than fixed-size windows — and embedded, tagged with company / doc-type / date metadata for filtering before search even happens.

ProcessingVoyage 4 Large embeddings
🚦

Confidence Gate

Every structured extraction returns a confidence score. Below threshold — an unusual clause, a number the model isn't sure it parsed correctly — it's routed to human review regardless of how "important" the field looks. Above threshold, it goes straight to Postgres. This is the one gate in the whole pipeline that can't be skipped for speed.

GateLangGraph conditional edge · threshold rule
🙋

Human Review Queue

A short worklist an analyst clears — confirm or correct a low-confidence extraction. Corrections feed back into the record as-verified, and over time also become a signal for where the extractor prompts need tightening.

Human-in-loopinternal Retool queue

ATLAS — Storage

Deliberately two different stores for two different question types
🐘

Postgres

Holds everything that came out of structured extraction: financial_metrics (time-series, one row per company per period), legal_terms (keyed clauses per SHA/term sheet), and a documents table tracking every ingested file's metadata and lineage. This is what "revenue last 3 months" hits — a normal indexed query, not a model guessing from text.

StoragePostgres 17 · Supabase-managed
🧠

pgvector

Holds doc_chunks — embeddings for everything that's inherently qualitative (deck narrative, transcript summaries, risk commentary), each tagged with company, doc type, and date so retrieval can pre-filter by metadata before doing the vector search itself. Same Postgres instance as the structured tables, different tables — one system to operate, not two.

Storagepgvector · HNSW index, cosine
📦

Object Storage

Every raw file, untouched, kept as the ground truth a citation can always be traced back to. If an extraction is ever disputed, this is what gets pulled up — the source of record behind every structured field and every chunk.

StorageS3 · versioned, lifecycle → Glacier

DELPHI — Query & Response

Route by question type, retrieve, generate, verify before it's shown
💬

Partner Question

The only interface a partner needs is natural language — "what's Bellatrix's burn rate this quarter" or "what risks has the founder flagged in the last two calls." No query syntax, no filters to set manually.

TriggerSlack bot + Next.js web chat
🔀

Question Router

Classifies the question itself: does this need a precise number from structured data, a qualitative synthesis from documents, or both? Financial and factual questions go to parametrized query; "why," "risk," and "how is X going" questions go to retrieval. Many real questions hit both paths and get merged at generation.

ProcessingClaude Haiku 4.5 · intent classifier
🎯

Parametrized Query

Deliberately not open text-to-SQL. The router maps the question onto one of a fixed set of parametrized query templates (metric, company, date range) and executes that — reliable and auditable, at the cost of not handling arbitrarily novel structured questions. New recurring question shapes get promoted into new templates over time.

ProcessingSQLAlchemy · parametrized templates
🔎

Hybrid Retrieval

Metadata filtering first (company, doc type, date window) to shrink the search space, then vector + keyword hybrid search within that filtered set. Filtering before searching is also the single biggest token-cost lever in the whole system — it keeps irrelevant chunks out of the context window before they're ever a cost.

Processingpgvector cosine + Postgres FTS (ts_rank)
📶

Rerank

A cross-encoder reorders the retrieved candidates for actual relevance to the question (vector similarity alone is a decent first pass, not a great final answer), and only the top few make it into the generation prompt.

ProcessingCohere Rerank 4 Fast
✍️

Generate + Cite

The frontier model in the system — everything upstream exists to hand it a small, high-signal context instead of a firehose. It's prompted to cite a source for every factual claim it makes, structured data and retrieved chunks alike, not just write a fluent-sounding answer.

AI stepClaude Sonnet 5 · forced-citation prompt
✅

Groundedness Check

Before an answer ever reaches a partner, a verification pass checks that every claim in it actually traces back to a cited source (structured field or retrieved chunk) — this is the main hallucination-reduction control, separate from and after generation, not just a prompting instruction.

GateNLI verifier + Claude Haiku judge rubric
💻

Answer + Sources

The final response, with every claim linking back to the underlying document, extracted field, or transcript it came from — so a partner can verify in one click rather than trusting the system blind.

OutputNext.js · streamed response

Token Economics

Seven levers, applied before generation ever runs — cheaper to filter than to trim after the fact
  • Metadata filter before vector search. Company / doc-type / date narrows the candidate set before embeddings are even compared — the single biggest lever.
  • Prefer structured lookup over RAG. If a question maps to a Postgres field, it never touches the retrieval pipeline at all.
  • Tight, topic-coherent chunking. Smaller, cleaner chunks mean fewer low-relevance tokens riding along into context.
  • Transcript summarization cascade. Raw call transcripts are summarized once at ingestion, not re-read in full on every query that touches them.
  • Model tiering. Cheap/fast models handle classification and extraction; the frontier model is reserved for final synthesis only.
  • Prompt caching. Stable system instructions and schemas are cached rather than resent on every call.
  • Caching of repeat queries. Common questions (e.g. recurring board-prep queries) reuse recent results instead of re-running the full pipeline.

Evaluation Strategy

Structured answers are graded differently than qualitative ones — because they should be
  • Deterministic evals for structured answers. Exact-match or tolerance-based checks against known-correct financial and legal fields — no ambiguity, so no judge model needed.
  • LLM-as-judge for qualitative answers. A grounding rubric scores whether a "what are the risks" style answer is actually supported by the cited sources, not just fluent.
  • Retrieval and generation evaluated separately. Bad answers get diagnosed as a retrieval miss vs. a generation/grounding failure — different fixes, so they can't share one metric.
  • Eval set grows from real usage. Every real partner question with a verified-correct answer becomes a regression test, not just a one-off.

Known Challenges

The honest list — none of these are fully solved on day one
  • Messy, inconsistent source formats. 30 companies means 30 different ways of writing a board deck or a term sheet — extraction prompts need constant tuning, not a one-time build.
  • Access sprawl. Docs live across Drive, email, and DocSend today — normalizing access and permissions across all three is real integration work, not a footnote.
  • Confidentiality boundaries. Per-company and per-partner access controls have to be correct from day one — this is fund-sensitive data, not a nice-to-have.
  • Transcript noise. Auto-generated transcripts have real error rates; summarization has to be robust to that noise, not assume clean input.
  • Staleness. A number that was true last quarter can quietly become wrong — every structured fact needs a visible "as of" date, not just a value.
